Standardizing QA Across 6 Squads

Mengantar · Quality Assurance Lead · 2025 - 2026

The problem

Our QA team (about 14 engineers across 6 squads) had no shared standard. Each QA used their own tools, test case format, and workflow. QA’s role inside each squad was barely visible: our work was seen as “just testing,” even though QA contributed from requirements all the way to release.

The goal

Give every squad one way of working, and make QA’s contribution visible and measurable beyond test execution.

What I did

  • Wrote the QA Guide Book: QA principles and mindset, QA’s role in every SDLC phase, and shared standards for task creation, test cases, bug reports, hotfix handling, and release preparation.
  • Designed a metrics framework: Feedback Adoption Rate, Early Feedback Ratio, Test Execution and Pass Rate, Feedback Fix Rate, and Defect Detection/Escape Percentage, each with a formula and clear thresholds.
  • Reviewed every standard and metric with the QA team before rollout, so each squad agreed on the approach before adopting it.
  • Introduced a quarterly QA audit that reports these metrics per squad.

Results

Feedback adoption rate
Q4 202577.3%→Q1 202695%→Q2 202699%
Defect escape rate
Q4 20255.3%→Q1 20264.9%→Q2 20263.6%

Team averages. Q4 2025 was the first audit.

  • Shift-left in practice: QA is now involved from pre-grooming and design review, not only after development.
  • Useful beyond QA: engineers use the per-sprint Fix Rate recap to complete their own sprint reports.
  • Trusted by management: the quarterly QA report is used to assess QA KPIs and serves as the evidence for quarterly performance bonuses.

What I’d improve next

Back every explanation of a metric drop with data, add owners and targets to each action item, define explicit release go/no-go criteria and hotfix severity levels, and keep refining metric thresholds based on real usage.

Ceria Belajar · Test Automation

Personal project · 2026 · Public repository

An end-to-end test suite for my own app, Ceria Belajar. Because the app is mine, everything is public: the code, the CI pipeline, and the live test report.

  • 72 automated test runs covering child profiles, medals, and stars, on desktop and a mobile viewport.
  • Found 3 bugs in the app’s reward system: 19 of 32 medals unlocked the wrong reward, the medal counter skipped one medal, and two screens showed different star counts for the same child. All three are fixed and now guarded by regression tests.
  • Surfaced accessibility gaps (controls that could not be used with a keyboard or screen reader, and an animation that ignored the reduce-motion setting) and fixed them in the app.
  • Readable reporting: every test states what it verifies and reads as Given / When / Then steps in the Allure report.

Approach: Page Object Model, test data seeded through localStorage instead of slow UI setup, accessibility-first locators, and known bugs tracked as expected-failure tests that flag themselves once the fix ships.

Tools: Playwright, TypeScript, GitHub Actions, Allure, GitHub Pages.
